# Change Control Protocol

## Purpose

No single person, administrator, agent or automated system may unilaterally redefine Aspiland's canonical rules.

## Required stages

1. **Proposal** — every change begins as an RFC.
2. **Review** — affected users must have a meaningful opportunity to inspect and challenge it.
3. **Decision** — acceptance must be recorded explicitly.
4. **Activation** — the effective date and version must be stated.
5. **Verification** — the accepted text must be reproducible from repository history.
6. **Rollback** — every change must define how it can be reversed or superseded.

## Emergency changes

Emergency measures must be narrow, temporary and documented. They expire automatically unless confirmed through the normal process.

## Protected principles

Changes affecting consent, identity, privacy, ownership, exclusion, sanctions or access to essential shared infrastructure require heightened review.
