# First Commit Kit

Status: public onboarding draft; non-canonical  
Edition: Repository Preview  
Last reviewed: 2026-07-12

Welcome to Aspiland.

You are not joining a legal state, accepting hidden terms or receiving a ceremonial identity. You are entering a public repository containing governance experiments, software, research, creative work and historical material.

The goal of the First Commit Kit is simple:

> Help a new participant understand one part of Aspiland and leave it clearer, safer or more useful than they found it.

## 1. Read the map

Begin with:

1. the root `README.md`;
2. `docs/glossary.md`;
3. `docs/current-status.md`;
4. `CONTRIBUTING.md`;
5. `CODE_OF_CONDUCT.md`;
6. `SECURITY.md` if your contribution touches data, credentials or infrastructure.

Remember the repository layers:

- `canon/` contains explicitly accepted and effective rules;
- `rfc/` contains proposals and decision records;
- `protocols/` contains recurring working procedures;
- `projects/` contains bounded experiments;
- `public/` contains reviewed public communication;
- `archive/` preserves history without making it current authority.

## 2. Choose a first contribution

Good first contributions are small, understandable and reversible.

### Documentation

- repair a broken or misleading link;
- explain an acronym or technical term;
- add a missing project status or dependency;
- improve a confusing paragraph without changing its meaning;
- identify where historical material could be mistaken for current policy.

### Accessibility and language

- improve heading structure or link descriptions;
- report low contrast, keyboard-navigation or screen-reader problems;
- translate a current public document while naming its source version;
- replace unnecessarily complex language with a plain-language explanation;
- document a sensory or communication accessibility gap without requiring diagnosis disclosure.

### Software and research

- reproduce and document a project setup problem;
- add safe run instructions;
- separate generated output from source files;
- add a small test or validation check;
- distinguish implemented behavior from an idea, simulation or claim.

### Governance

- ask a precise question about scope, authority, consent, review or rollback;
- identify a contradiction between current documents;
- propose a bounded RFC using the repository template;
- add evidence to an existing proposal without presenting it as accepted;
- suggest a safer or more reversible implementation.

## 3. Check the boundaries

Before submitting:

- do not include passwords, tokens, private keys, recovery codes or private infrastructure details;
- do not publish unnecessary personal, health, contact or identity data;
- do not copy third-party text, artwork or code without confirming the applicable rights;
- do not present fiction, satire, archive material or proposals as current fact;
- do not claim that Aspiland is a sovereign state, legal jurisdiction, investment or production public service;
- do not assign yourself or an automated system authority over other people;
- do not make irreversible changes when a reversible path exists.

Report an active secret or privacy exposure privately according to `SECURITY.md`. Do not open a public issue containing the exposed value.

## 4. Write the contribution

A useful change description answers:

- What changed?
- Why does it matter?
- Which repository layer or project is affected?
- Does it change meaning, authority, privacy, security or public claims?
- How was it checked?
- What remains uncertain?
- How can it be corrected or rolled back?

Suggested title patterns:

- `Clarify the status of ...`
- `Document safe setup for ...`
- `Fix navigation to ...`
- `Propose ... through RFC`
- `Separate historical ... from current ...`
- `Add accessibility guidance for ...`

## 5. Submit through the right path

- documentation or software correction: pull request;
- question, reproducible problem or scoped idea: issue;
- governance or authority change: RFC first;
- active credential or personal-data exposure: private security report;
- historical discovery with unclear status: document provenance and request classification.

A merged proposal is not automatically accepted governance. Canonical status requires the applicable decision and effective-date process.

## 6. First contribution checklist

- [ ] I know which layer or project I changed.
- [ ] I did not include secrets or unnecessary personal data.
- [ ] I did not confuse historical, fictional, proposed and accepted material.
- [ ] I stated the purpose and impact.
- [ ] I documented validation or uncertainty.
- [ ] I included a correction or rollback path when the change is consequential.
- [ ] I followed the code of conduct.

## 7. After the first commit

There is no automatic legal citizenship, rank, ownership or authority attached to a contribution.

What you gain is more useful: a visible piece of evidence that you understood part of the world well enough to improve it.

Possible next steps:

- help review another small contribution;
- document an active project;
- improve public communication;
- test onboarding as a new reader;
- join discussion around a proposed RFC;
- identify a missing safety, privacy, accessibility or continuity control.

## Certificate text

A future generated certificate may use the following wording:

> **First Commit to Aspiland**  
> This record recognizes a reviewed contribution that made the repository clearer, safer or more useful. It grants no legal identity, ownership, financial value or governance authority. The contribution and its history remain the source of truth.

The certificate must link to the contribution or decision record and must not include personal data beyond what the participant intentionally publishes.
